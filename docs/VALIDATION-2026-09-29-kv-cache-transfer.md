# Synthetic KV-cache transfer validation (2026-09-29)

## Object represented by the test

The transferred byte object models one BF16 K+V layer at a 128 Ki-token
context length:

```text
2 (K and V) * 1 layer * 131072 tokens * 8 KV heads
  * 128 head dimension * 2 bytes = 536870912 bytes (512 MiB)
```

The contents are deterministic synthetic bytes generated by global object
offset.  This tests transport, authenticated placement, and exact private
reassembly; it is not a framework-specific tensor serializer.

The object is divided into 387,913 authenticated chunks with up to 1,384 data
bytes each.

## Basic tests before the large transfer

- Host protocol test: all wire, integer-boundary, AEAD-tamper, first-packet
  allocation, replay, cross-object, ACK, and reassembly cases passed under
  strict `-Werror` flags.
- The same protocol test passed inside `cvm26-snp` against OpenSSL 3.5.5.
- GCC `-fanalyzer` reported no issue in the receiver test or sender.
- ASan/UBSan passed; only LeakSanitizer was disabled because it cannot run
  under the managed ptrace environment.
- `ninja -C build app/dpdk-testpmd` was up to date and successful.
- A no-fault 1 MiB baseline completed 758/758 chunks with no retransmission,
  matching source/private SHA-256, and zero NIC missed/error/nombuf counters.

## Problem found and fixed

The first 512 MiB run completed byte-exactly and had zero NIC missed/error
counters, but the sender's fixed 20 ms retransmission timeout generated 590
spurious retransmissions.  The CVM received those as exactly 590 authenticated
duplicates.  A 100 ms trial reduced this to 130 but did not eliminate the
unnecessary traffic.

The host and CVM forwarding threads are not pinned, and this prototype does
not yet implement an RTT estimator.  The sender therefore now uses a
conservative one-second initial RTO, consistent with correctness-first behavior
under scheduling tail latency.  A future latency-oriented sender should use a
Karn/Jacobson RTT estimator instead of selecting another small fixed constant.

The synthetic sender was also changed to calculate source SHA-256 in a bounded
streaming buffer.  It does not allocate a second copy of the object.  This
makes the end-to-end comparison part of the sender/receiver logs rather than a
manual post-processing step.

These changes affect only `scratch/cvm-chunk-proto/cvm_chunk_send.c` and its
README.  They do not alter the wire format, mlx5, the kernel module, the
shared/private mbuf bridge, or the DPDK receiver.

The three rejected RX frames were unrelated 60-byte/background traffic that
did not match the fixed authenticated endpoint.  They were not chunks from the
test object.

Therefore the final run had no missing protocol chunks, no retransmissions, no
authenticated duplicates, no NIC misses/errors, and a byte-identical private
result.  The reported 1.300 Gbit/s is a measurement of this single-core,
per-packet-AES-GCM, per-packet-ACK correctness prototype, not a tuned KV-cache
transport result.
